# Decisions for tickets 02, 08, 09, 10

Defaults chosen where the tickets leave things open. Override any by editing this file before the ticket starts. Implementers follow these; a reviewer treats a deviation as a finding.

## 02 Write a Recipe by hand

- **Ingredient** is global: one `ingredients` table, unique on the normalised name. Any signed-in user can read and insert; nobody updates or deletes.
- **Normalising a name** (the Ingredient matcher, `src/data/ingredient-matcher.ts`; replaced 2026-10-25, a general English plural library kept failing on food words): NFC; lowercase, locale-independent ("İSOT" keeps its dot as a combining mark, never "i sot"); remove apostrophes (' and ’); keep letters, combining marks and numbers (`\p{L}\p{M}\p{N}`), every other character becomes a space; collapse and trim whitespace. Then singularise only the last word, with our own ordered rules and no plural library: an uncountable set (unchanged: molasses, schnapps, bitters, haggis, pastis…), an irregular map (leaves → leaf, quiches → quiche…), an `-ie`/`-i` set for `-ies` words (cookie, brownie, veggie, smoothie, pie, chilli, chili…), then `ies → y`, `oes → o`, `(ch|sh|x|ss|z)es` → drop `es`, else drop a trailing `s` unless the word ends in `ss` or `us` or has ≤ 3 letters (so plurals of `-i` words lose it: "chilis" → "chili", "zucchinis" → "zucchini"). So "Garlic", "garlic " and "garlics" give "garlic"; "tomatoes" gives "tomato"; "hummus", "molasses" and "couscous" are unchanged; "Hellmann's" gives "hellmann"; "M&M's" gives "m ms". An empty result is a missing Ingredient (a validation error). The spec is the table in `tests/ingredient-matcher.test.ts`: a food word it gets wrong becomes a new row there plus an entry in one of the sets. No fuzzy matching.
- The matcher is frozen after this: further rare misses are known limits, fixed by relinking a line, not reasons to block a ticket.
- **Typed lines**: each line has its original text, optional amount text and a required Ingredient name the user fills in or edits.
- A hand-made Recipe is `status = 'reviewed'`, `recipe_found = true`. Steps are an ordered list; lines have a position. `editRecipe` replaces all lines in one transaction (RPC). The library lists the user's reviewed Recipes, newest first.

## 08 Pantry and Staples

- Default Staples (salt, pepper, oil) are seeded by a trigger on Profile insert; the migration backfills existing Profiles.
- Pantry, Staples: owner-only RLS now. Ticket 15 will expose "who has it" to Cook Plan members; don't build that now.
- "Used up" deletes the Pantry entry. Staples change one at a time through `addStaple` / `removeStaple` (one-row insert `on conflict do nothing` / delete), so concurrent changes never clash or undo each other; the spec's `setStaples` (a full replace) is dropped. A Staple always counts as in the Pantry.
- **Counts as present** has one definition: `private.ingredients_had(user)` in the 08 migration (Pantry entry or Staple, one row per Ingredient). `has_ingredient` and `ingredients_i_have` (`listIngredientsIHave`, for ticket 09's list engine) wrap it for `auth.uid()`; ticket 15's member-scoped wrapper calls it too. Nothing else restates the rule.

## 09 Shopping List

- One Shopping List per user, created by trigger (backfill existing users).
- Hand-added items only look up an existing Ingredient by normalised name; they never create one. The match is stored when the item is added. So "paper towels" matches nothing and checking it off changes no Pantry.
- `checkOff` is a security-definer RPC that writes the **list owner's** Pantry, so ticket 13 (shared lists) needs no rewrite.
- Unchecking leaves the Pantry alone.
- `add_recipe_to_shopping_list` takes the list engine's lines but trusts only what it can check (PR #1 review): an Ingredient id not on one of that Recipe's lines is refused (22023), and the Ingredients the user has are left off as `private.ingredients_had` says inside the RPC, not as the phone read them before calling it. It returns the Ingredients it put the Recipe on the list for.
- Adding the same Recipe twice changes nothing. Deleting a Recipe removes its amount rows; an unchecked line with no amounts left is removed.
- **For ticket 13:** Friends on a shared list must see the Recipe titles on its lines, but Recipes are owner-only, so `recipe:recipes(id, title)` comes back null for a Friend and `toShoppingListItem` (`src/data/data-layer.ts`) throws; ticket 13 either stores the title on the amount row or adds a list-scoped policy on Recipes. `add_manual_item` takes the list id now and refuses a list the caller can't use (PR #2 review, see 10); `add_recipe_to_shopping_list` and `getShoppingList` act on the caller's own list today and will need one.
- **For ticket 13, too:** any signed-in user can insert into and read the global `ingredients` table (decision 02). Before lists are shared, revisit who may write it (PR #1 review).

## 10 Lists work with no signal

- **Conflicts resolve by when each change was made** (decided by the human, 2026-10-24). Each queued change carries the phone's timestamp; an RPC compares it with the item's `phone_changed_at`, the time of the last change a phone made to that item (check, uncheck, add by hand, each with its own `changed_at`), and skips an older change. Writes the server makes by itself (adding a Recipe's lines, unchecking a line a new Recipe needs) stamp `updated_at` with the server's clock and never move `phone_changed_at`, so phone and server clocks are never compared (PR #1 review: a phone a few seconds slow couldn't check off a line just after adding its Recipe). Skew between phones is accepted. `check_off` and `uncheck` say `applied`, `superseded` or `gone`; on `superseded` the phone takes the change off the queue without applying it to the list it shows, and reads the list again.
- No new native module: a failed request means offline; retry on app foreground and on a timer. The data layer takes an injectable transport/connectivity switch so tests can go offline.
- Offline you can check, uncheck and add hand items. Removing needs a connection. Items added offline get a client-made UUID so replays are idempotent. Changes to an item deleted meanwhile are dropped. The last-seen list is cached in AsyncStorage.
- **Signing out ends the session on this phone at once, signal or not** (fix round 2). The data layer clears the auth client's saved session itself (through `createSessionStorage`, the auth client's `auth.storage`), forgets the remembered user, then asks the server to end this phone's session (scope `local`) if it can be reached. The user's other phones stay signed in. With no signal the server keeps that session until its refresh token expires; the phone no longer has it.
- **A session ends on this phone in one place, `endSessionOnPhone`, and sign-ins take turns with it** (fix round 4). Signing out, the auth client dropping a session whose refresh the server refused (`SIGNED_OUT`), and a cold start with no usable session all call it; it clears the saved session, forgets the user, discards their queued list changes and cached list, then reports signed out. Sign-ins and session ends run one at a time in the order asked, so a sign-in waits for a sign-out still finishing. An end the auth client asked for is dropped if anyone signed in or out since, or if the auth client holds a session not ended here. The server-side end uses the access token of the session just cleared (the admin `logout` call), never the auth client's current session, and the data layer no longer calls the auth client's `signOut`: in supabase-js 2.118 that waits for the client's start-up refresh (about 25 s with no signal) and then ends whichever session it holds by then, which could be the next user's. A session whose access token had run out isn't ended on the server (refreshing it would hand the auth client a session again). Sessions the auth client still reports after they were ended here are ignored, and the auth client's storage adapter (`createSessionStorage`) refuses to save one again, so a refresh that lands after the sign-out can't sign the user back in, now or after a restart (ticket 20). Whether a failed refresh ends the session is decided in one place, `refusesSession`, on a cold start, on `SIGNED_OUT`, and on a 401's refresh alike: it ends when there was no session at all (`AuthSessionMissingError`), or when the auth server itself refused the refresh, a JSON answer (`AuthApiError`) with status 400, 401 or 403, whatever its code (a revoked or reused refresh token, a banned user, `validation_failed` alike). It isn't a list of codes, which missed `user_banned` and `validation_failed` and left a banned user signed in for good. Everything else is no answer about the session: no signal, a 408, a 429, a 5xx, or a body that isn't the auth server's JSON (`AuthUnknownError`, such as a proxy's error page). The auth client drops its session on any refresh error but a network failure once the access token has run out (a 429, a 408, a proxy's error page too), so the storage adapter never lets it remove a saved session: only `endSessionOnPhone` does, and on anything `refusesSession` doesn't call a refusal the user stays signed in with their queue, and the session is refreshed later.
- **List changes still waiting when the user signs out are discarded**, with the list the phone last saw. The same goes for every way a session ends on the phone, including a refresh the server refuses (fix round 4): both are removed from storage, and a send or read that finishes afterwards writes nothing back. Keeping them for that user's next sign-in would leave their list on a phone they signed out of, and send changes days later, unseen. Discarding can lose a check made in a dead zone just before signing out; that's the safer loss.
- **A change the server keeps failing on is retried with backoff, and given up after about 21 minutes of server errors (5xx)** (fix round 3, replacing round 2's 5 errors in a row, which a one-minute outage reached at one try every 10 s). After each 5xx in a row the change waits 10 s, 30 s, 1 min, 5 min, then 15 min before its next try; when the try after the 15-minute wait fails too (its first try and 5 retries), it's given up. The count and the next-try time are saved with the queued change, so they outlive restarts, and every trigger respects the next-try time: the 10 s timer, the app coming to the foreground, a new change, and an explicit sync. The changes behind it wait for it, as the queue keeps order. No answer at all (offline, 408, 429) never counts, and doesn't move the next try. A 401 (PR #1 review: an access token the server refuses, with no `SIGNED_OUT`, left the queue offline for good) refreshes the session once and makes the request again: no signal for the refresh is offline; a refresh the server refuses ends the session on this phone through `endSessionOnPhone`, even when the auth client keeps it because its access token hasn't run out by the phone's clock; a 401 again after a refresh that worked counts like a server error. A next-try time further off than the change's own pause plus a minute means the phone's clock went back past the failure, so the change is tried (fix round 4: comparing with the longest pause alone made any step back during the 15-minute pause send it at once). Giving up refuses the change and takes it off the queue, so the changes behind it sync, and the Shopping List shows "Couldn't check off Foil." (uncheck, add likewise) until the user taps OK. The changes given up are saved with the queue, named as the list showed the item when it was given up, so the notice outlives a restart and the item's removal; OK forgets them on this phone for good. A change that fails a few times and then gets through lands as usual. A send that throws (a bug, not an answer from the server) is given up at once the same way, with the same notice, and logged (PR #1 review: it was dropped silently).
- **A queued change goes out only as the user who made it, and only to their list** (PR #2 review: a hand-add whose first send got a 401 was sent again after the refresh with whatever session the auth client held by then, so if the user signed out and someone else signed in meanwhile it landed on the newcomer's list). Every request a queued change makes, the one after a 401's refresh included, is checked just before it goes out (`asSignedIn`, given the user and `discarded`): the auth client's session is still that user's, the same session (`sessionIdOf`) the first request went out with, not ended on this phone, and their queue isn't discarded. The refresh is checked for likewise before it starts. The request carries that session's access token itself, so it can't pick up a session signed in since. If the check fails nothing is sent: the change waits, as with no usable session, or goes with the queue if it was discarded. (While the refresh is on the way, the auth client itself drops a refresh whose saved session changed meanwhile.) `refusesSession` stays the one rule for a refused refresh. The server checks too: `add_manual_item` takes the list the item is for and returns null unless the caller can use it (`private.can_use_shopping_list`), so an add sent with another user's session fails closed, as a check-off of another user's item already did (`gone`); `added`, `gone` and `taken` are unchanged. The phone has the list id from the list it last saw, or reads the list before queuing the first add. A hand-add an older version queued without its list is for the list the phone saved for the same user, read back first; with none saved, it's skipped as unreadable.
- **Waiting out a server error isn't being offline** (fix round 4). While the change at the head of the queue waits for its next try, the queue (and `ListSync`) is `waitingToRetry`, with `retryAt`, not `offline`, and the Shopping List says "The server had a problem. N changes will retry shortly." A list read that gets a 5xx doesn't mark the phone offline either. Removing works then, as the server can be reached: it sends its own delete, and on success the item's changes still waiting are taken off the queue (an add waiting would put the item back, and the rest would change an item that's gone), so they're neither sent nor reported as given up. If the delete itself gets a 5xx, Remove says the server had a problem, not that the phone is offline.

## 03 Save a TikTok link into a Draft

- **A Draft is a Recipe with `status = 'draft'`** (spec L203, L226), plus a new `build_status` enum column: `building` → `built` or `failed`; `failed` → `building` on Retry. Check: `status = 'reviewed'` implies `build_status = 'built'`. Hand-made Recipes are inserted `built` (decision 02 unchanged). More columns: `build_failure` (null unless failed), `build_attempts int`, `build_started_at timestamptz` (null until a builder claims it). `recipe_found` stays as it is (defaults true, the builder sets it). In the domain, `Recipe` keeps `status: 'draft' | 'reviewed'` and `recipeFound`, and gains `build: { status: 'building' } | { status: 'built' } | { status: 'failed'; reason: 'sourceUnavailable' | 'sourceUnreachable' | 'unreadable' | 'timedOut'; canRetry: boolean }`. A row still `building` whose `build_started_at` is over 3 minutes old reads as `failed`/`timedOut`. The row is worked out by `toRecipe`; no stored state is added for it.
- **Build columns are written only on the server.** Replace the table-wide `update` grant on `recipes` with column grants for what the owner may change (`title`, `steps`, `updated_at`, plus 06's columns). `build_*`, `status` and `recipe_found` change only through RPCs. `reviewDraft` is one of these: a security-invoker RPC that replaces the title, steps and lines like `edit_recipe` and sets `status = 'reviewed'`, `build_status = 'built'`. It refuses a Draft that is still `building`, and it accepts a `failed` one ("Fill in by hand"). Editing a Draft while it builds is not offered.
- **The Source Video** is a `source_videos` row, 1:1 with its Recipe (`recipe_id unique`, cascade). It holds `platform` (`tiktok`, `youtube`, `instagram`, `web`), `original_url`, `external_id`, `creator_name`, `creator_url`, `caption`, `title`, `thumbnail_url`, `recipe_site_url`, `screenshot_path`, `pasted_text` and `fetched_at` (spec L206). The owner can read it through the Recipe. Only the server writes it. The Recipe screen shows the thumbnail and creator. Tapping it runs `Linking.openURL(original_url)`, which opens the TikTok app through its universal link.
- **What "saving returns at once" means** (spec L226): `saveFromLink({ url, text?, screenshot? })` makes the Recipe id on the phone (like list items, decision 10) and calls the security-definer RPC `save_from_link`. In one transaction, that RPC checks the daily limit (07), then inserts the Recipe, its `source_videos` row and a `link_saves` row. The Recipe gets `status = 'draft'`, `build_status = 'building'` and a placeholder title ("TikTok video", "YouTube video", "Instagram Reel", or the host name). The RPC returns `{ status: 'saved', recipeId }`. The data layer then *kicks* the build by calling the Edge Function `build-draft` with `{ recipeId }`, and waits only for its `202`, with a 10 s timeout. The function checks the caller's JWT and that the Recipe is theirs. It answers `202` and builds inside `EdgeRuntime.waitUntil`. A failed kick (no signal, 5xx) doesn't fail the save. `resumeDraftBuilds()`, run on app foreground and when the Drafts list opens, kicks again every `building` Draft that is unclaimed and over 30 s old, or claimed over 3 minutes ago. Restarting a timed-out build this way claims the Draft again, which uses up one of its 3 attempts, just as a Retry does (review of ticket 03). We don't use a pg_net trigger: in tests it would call the real Edge Function and reach the network.
- **Each build claims its Draft first.** `claim_draft_build(recipe_id)` sets `build_started_at = now()` and adds one to `build_attempts`. It succeeds only while the Draft is `building`, unclaimed or claimed over 3 minutes ago, and has `build_attempts < 3`, so a double kick builds once. Then `finish_draft(recipe_id, result jsonb)` or `fail_draft(recipe_id, reason)` runs; both are security definer and granted to `service_role` only. `finish_draft` writes the title, steps, lines (through the same insert-Ingredient-then-link path as `private.replace_recipe_lines`), `recipe_found` and 06's suggested Tags. It does this only if the Draft is still `building`, and it returns whether it made the change, which 07 uses to send exactly one push. `fail_draft` sets `failed` and the reason.
- **Retries and failure display.** Within one attempt: the Claude call uses the SDK's own retries (`maxRetries: 2`, which covers 408/409/429/5xx and connection errors), and each source fetch is retried once after a network error or 5xx. The whole attempt has a budget of 120 s (the hosted wall clock is 150 s). Across attempts there is no automatic retry: the Drafts list shows "Couldn't build this Draft" with a reason line and Retry (while `build_attempts < 3`) and "Fill in by hand". Reason lines: `sourceUnavailable` (oEmbed 400/404) says "TikTok didn't return this video. It may be private or deleted."; `sourceUnreachable` says "Couldn't reach TikTok."; `unreadable` (refusal, `max_tokens`, output that fails validation) says "Couldn't read a recipe from it."; `timedOut` says "This took too long." `retryDraft(id)` sets the Draft back to `building` (an RPC that refuses after 3 attempts) and kicks it. A failed build sends no push (spec L238).
- **"Recipe not in caption"** (spec L228): when the builder says `recipeFound` is false, `finish_draft` stores no lines and no steps, whatever the model returned, and keeps its title. The Draft screen shows the "Recipe not in caption" banner above empty fields.
- **The source reader** (spec L162) lives in `supabase/functions/_shared/source-reader.ts` and is runtime-neutral: no `Deno`, no URL imports, no `@supabase/*`. The app never fetches a source. It only runs the pure `detectSource(url)` from the same folder to pick the save screen. Signature: `createSourceReader(adapters).read(shared: { url, text, screenshotPath }, signal): Promise<SourceMaterial>`. `SourceMaterial` is `{ platform, kind: 'video' | 'recipeSite' | 'page', originalUrl, externalId, title, caption, creatorName, creatorUrl, thumbnailUrl, siteRecipe, recipeSiteUrl, pastedText, screenshotPath }`. On failure it throws `SourceError { reason: 'unavailable' | 'unreachable' }`. `detectSource` sends `tiktok.com`, `vm.tiktok.com` and `vt.tiktok.com` to TikTok, and everything else to the `web` path (04 and 05 add hosts). A shared text with no URL of its own ("Check out… https://vm.tiktok.com/…") uses the first URL in the text.
- **The TikTok adapter** calls `GET https://www.tiktok.com/oembed?url=…` with no auth. `title` is the caption; it also takes `author_name`, `author_url` and `thumbnail_url`. The external id is `embed_product_id`, or else `/video/(\d+)` from the URL. A short link is passed as shared; when oEmbed returns 400, the adapter follows the short link's redirects (status only, no page body) and tries once more with the full URL. This is the only TikTok route (ADR-0004).
- **The Draft builder** is `buildDraft(recipeId, deps)` in `supabase/functions/_shared/draft-builder.ts`, which is runtime-neutral too. Its deps are `{ rpc, readSource, extract, loadScreenshot, sendPush, now }`. `supabase/functions/build-draft/index.ts` is a thin Deno entry. It wires the real adapters, the `npm:@anthropic-ai/sdk` extractor, a service-role `rpc` and Expo push. Its own `deno.json` sets `"unstable": ["sloppy-imports"]` so `_shared` can use extensionless imports like the app. Exclude `supabase/functions/*/index.ts` from `tsc` and eslint. If the CLI bundler refuses imports from `_shared`, stop and ask; don't copy the core into the function.
- **The Claude call** is the `extract(material, signal)` dep, made with the Anthropic TypeScript SDK (not raw `fetch`). Settings: `model: 'claude-haiku-5-5'` (spec L168), `max_tokens: 8000`, `output_config: { effort: 'low', format: { type: 'json_schema', schema } }`, no `thinking` or `temperature` fields, and `timeout: 60_000`. The schema is `{ title: string, recipeFound: boolean, lines: [{ text: string, amount: string | null, ingredient: string }], steps: string[] }`; 06 adds `tags`. Check `stop_reason` before parsing: `refusal` or `max_tokens` is `unreadable`. Parse with `JSON.parse` and check the shape by hand; a mismatch is `unreadable`. The system prompt says: use only what the text or image shows and never invent; `recipeFound` is false unless there is an ingredient list ("link in bio", "recipe in comments" mean false); `ingredient` is the plain food with no amount or preparation ("2 cloves garlic, minced" → "garlic"); `amount` is the quantity text as written. The caption is untrusted data inside the user turn; there are no tools. Cost at about 3k input and 1.5k output tokens is roughly $0.001 a Draft ($0.10 / $0.50 per MTok).
- **Linking lines to Ingredients** reuses decision 02 unchanged. The builder passes each `ingredient` through `normaliseIngredientName` (the frozen matcher). A line whose name normalises to empty is dropped. The Ingredient is found or created by its normalised name, as hand-written lines are. There's no fuzzy matching and no list of the user's known Ingredients in the prompt. A wrong link is fixed by relinking on review (spec L49).
- **The API key** is `ANTHROPIC_API_KEY` in `supabase/.env` (git-ignored by the `.env` rule), listed empty in `supabase/.env.example` and passed through `[edge_runtime.secrets]` in `config.toml`. On the hosted project it is set with `supabase secrets set`. It is never an `EXPO_PUBLIC_*` value and never in the app bundle.
- **Faking it in tests** (spec L263): the harness gives the data layer a new `DataLayerOptions.startDraftBuild(recipeId)`. In the app it is the `build-draft` kick. In tests it runs `buildDraft` in-process with a service-role `rpc` from `tests/harness.ts`, fake adapters with canned captions passed to the real `createSourceReader`, a fake `extract` that returns a canned extraction for each caption, and a recording `sendPush`. The harness tracks the build's promise so a test can `await drafts.settled()` before it asserts. The tests make no network calls. The JWT check in the Deno entry isn't exercised by tests. `drafts.access.test.ts` instead proves that a user can't call `claim_draft_build`, `finish_draft` or `fail_draft`, can't write `build_*` columns, `source_videos` or `link_saves`, and can't read another user's Drafts or Source Videos. Maestro flows run the functions with `supabase functions serve --env-file supabase/.env.e2e`, where `DRAFT_FIXTURES=1` wires the same fakes. The entry refuses that mode unless `SUPABASE_URL` is local. A flow opens the save screen with a `recipeapp://save?url=…` deep link, because nothing can share into the app from TikTok on the simulator.
- **Where Drafts show up.** 03 builds the Drafts list (`listDrafts()`: every `status = 'draft'` Recipe in any build state, newest first), reached from a "Drafts (n)" row at the top of the Library. 07 adds the push that opens a Draft. The Library itself still lists only reviewed Recipes (decision 02). Drafts stay unreviewed until the user acts (spec L37).
- **Native modules:** `expo-share-intent` (spec L144) needs a new development build. Its iOS activation rules accept 1 web URL, 1 text and 1 image. If it costs nothing extra, install `expo-image-picker`, `expo-image-manipulator` and `expo-notifications` in the same build; their JS stays with 05 and 07. That saves two more cloud builds.

## 04 YouTube Shorts, recipe-site and other links

- **YouTube uses the Data API v3, not oEmbed** (spec L164, ADR-0004, ticket 04): oEmbed has no description. The adapter calls `videos.list?part=snippet&id=…` with `YOUTUBE_API_KEY` from `supabase/.env`, kept like the Anthropic key. It takes `snippet.title`, `snippet.description` (as the caption), `channelTitle`, `channelId` (giving `https://www.youtube.com/channel/{id}`) and the best of `maxres`, `high`, `medium` thumbnails. An empty `items` array is `sourceUnavailable`. `detectSource` reads the video id from `youtube.com/shorts/{id}`, `youtu.be/{id}` and `youtube.com/watch?v={id}`; any YouTube video is accepted, not only Shorts. The card shows "YouTube · {channel}" (spec L293).
- **30 days** (spec L207, L293): when `getRecipe` loads a YouTube Recipe whose `fetched_at` is over 30 days old, it awaits a refresh (up to 5 s) before returning. A daily `pg_cron` job also clears `caption`, `title`, `thumbnail_url` and `creator_*` on YouTube `source_videos` older than 30 days, so stored API data never outlives the window, even for a Recipe nobody opens. Reviewed Recipe text is the user's own, and the job doesn't touch it.
- **Refreshing a thumbnail** (spec L208, L294): when the image fails to load, the screen calls `refreshSourceVideo(recipeId)`. The Edge Function `refresh-source-video` reads the TikTok or YouTube adapter again and updates `thumbnail_url` and `fetched_at`. It refuses a second refresh for the same Recipe within 10 minutes, and the screen then shows the plain card. Thumbnails are stored only as platform URLs, never copied (ADR-0004).
- **One page reader handles both recipe sites and other links**: it makes a single fetch. If the page's `<script type="application/ld+json">` holds a schema.org `Recipe` (inside an array, an `@graph`, or with `@type` as a string or an array), the result is `kind: 'recipeSite'` with `siteRecipe { name, ingredients: recipeIngredient[], steps (from a string, HowToStep[] or HowToSection.itemListElement), imageUrl, author }`. Otherwise it is `kind: 'page'` with `<title>` or `og:title` and `og:image`. `readSchemaOrgRecipe(html)` and the Open Graph reader are pure functions in `_shared`, with plain unit tests over HTML fixtures. The network adapter itself isn't unit-tested (spec L263).
- **Following a recipe-site link in a caption or description** (spec L39): the reader tries the first 3 URLs in the text, in order, skipping platform and Meta hosts. The first page with a schema.org Recipe wins and is stored as `recipe_site_url`. The extractor gets both the caption and the site Recipe, with an instruction to take lines and steps from the site Recipe. A recipe-site link shared directly goes through Claude the same way, which keeps one linking path.
- **Any other link** (`kind: 'page'`): there is no Claude call. The Draft is built with `recipe_found = false`, the page title as its title, and no lines or steps (ticket 04). The card shows `og:image` as a URL (not copied), and tapping it opens the browser.
- **Every server fetch of a link from the user or a caption goes through `safeFetch` in `_shared`**: `http`/`https` only; no IP-literal hosts and no `localhost`, `*.local` or `*.internal`; Meta hosts refused (see 05); at most 5 redirects, each re-checked; an 8 s timeout; at most 2 MB read; `text/html` only; the User-Agent `RecipeApp/1.0`. DNS rebinding isn't handled (accepted for TestFlight).

## 05 Instagram via screenshot or pasted caption

- **No network call to Instagram, ever** (ADR-0004, spec L165). `detectSource` maps `instagram.com/reel/`, `/reels/`, `/p/` and `instagr.am` to `instagram`, with the shortcode as `external_id` and no creator. The Instagram adapter is pure: it returns the link, the pasted text and the screenshot path. `safeFetch` refuses `instagram.com`, `instagr.am`, `cdninstagram.com`, `facebook.com`, `fb.watch`, `fbcdn.net` and `threads.net` and their subdomains, so a caption link to them isn't followed either. A unit test over `safeFetch`'s host check proves it.
- **The save screen** (spec L224–L225) offers "Add screenshot" (`expo-image-picker`, library only) and "Paste caption" (a text field), and both may be used together. With neither, the save still goes through, the builder makes no Claude call, and the result is a recipe-not-in-caption Draft titled "Instagram Reel".
- **Screenshots are the user's own images** (spec L209). They go in a private Storage bucket, `recipe-images`, at `{user_id}/{recipe_id}.jpg`. `storage.objects` policies scope it to the first path segment `= auth.uid()`. The phone downscales the image to at most 1568 px on the long edge and saves it as JPEG at quality 0.8 (`expo-image-manipulator`). It uploads the file *before* calling `save_from_link`, which records `screenshot_path`; that is the one wait before "Saved". The builder's `loadScreenshot` downloads it with the service role and sends it to Haiku as a base64 `image` block before the text block. Pasted text goes in as text, and its links are followed as in 04.
- **The picture**: the screenshot (a signed URL valid for 1 hour, made by `getRecipe`), or else a plain Instagram card drawn with `src/ui` tokens. It uses the word "Instagram", not the logo. Tapping it opens the Reel URL.

## 06 Tags, search and Want to Cook

- **Tags are per user** (spec L212): `tags (id, owner_id, name)`, unique on `(owner_id, lower(name))`. The name is trimmed with spaces collapsed, keeps its first spelling, and may be at most 40 characters. The join table is `recipe_tags (recipe_id, tag_id)`. Both are owner-only through RLS. A Tag with no Recipes left stays in the user's Tag list until they delete it.
- **Suggested Tags** (spec L52): the builder schema adds `tags: string[]` (at most 5: cuisine, meal type, and "quick" when the Recipe takes 30 minutes or less). `finish_draft` stores them as `recipes.suggested_tags text[]`, not as Tags. The Draft screen shows them as chips, already selected, matched to the user's existing Tags without regard to case. `reviewDraft` takes the selected Tag names and creates or attaches them, then clears `suggested_tags`. So unreviewed Drafts never fill the Tag list. Actions: `addTag(recipeId, name)`, `removeTag(recipeId, tagId)`, `listTags()`, `deleteTag(tagId)`.
- **Search** (spec L54) is the security-invoker RPC `search_recipes(query)` over the user's *reviewed* Recipes. The query is split into words. A Recipe matches when every word matches somewhere: as a case-insensitive substring of the title, as a substring of a linked Ingredient's name (the word normalised by the matcher first, so "tomatoes" finds "tomato"), or as a substring of a Tag name. Results come newest first. An empty query gives the Library. There is no fuzzy or full-text search.
- **Want to Cook** (spec L56, L203) is `recipes.want_to_cook_at timestamptz null`. Null means not marked; the timestamp orders the list, most recently marked first. It is set only on reviewed Recipes. Actions: `setWantToCook(recipeId, on)` and `listWantToCook()`. The domain gives `wantToCookSince: string | null`. Owner-only, like the rest of the Recipe.

## 07 Push notifications, "Draft ready" and the daily limit

- **Push tokens** (spec L219): `push_tokens (token text primary key, user_id, created_at, last_seen_at)`. `registerPushToken(token)` is a security-definer upsert on `token` that sets `user_id = auth.uid()`, so a phone that changes hands moves to the new user. Signing out deletes this phone's token if the server can be reached (best effort, alongside `endSessionOnPhone`). When an Expo push ticket reports `DeviceNotRegistered`, that token is deleted. Users read only their own rows and write none directly. Accepted (ticket 07 review, 2026-10-28): anyone who knows a push token can take it over by registering it, and then gets that phone's "Draft ready" pushes instead of its owner. Tokens are never readable through RLS (each user sees only their own), and moving to whoever registers last is by design, for a phone that changes hands.
- **Asking for permission**: `expo-notifications` asks after the user's first successful link save, not at launch. It gets the token with `getExpoPushTokenAsync({ projectId })` (the EAS project id in `app.config.ts`) and registers it again on each app foreground. If permission is denied, nothing is stored and saving works as before.
- **"Draft ready"** (spec L175, L238): it is sent from `buildDraft` only when `finish_draft` reports that it made the change, so a double kick or a retry sends exactly one push. It goes to all of the owner's tokens through `POST https://exp.host/--/api/v2/push/send` (with `EXPO_ACCESS_TOKEN` from `supabase/.env` if enhanced security is turned on). The payload is title "Draft ready", body the Draft's title, `data: { kind: 'draftReady', recipeId }`. A recipe-not-in-caption Draft still gets it. A failed build gets none. Tapping it opens that Draft (a notification response listener routes to the Draft screen). A push that can't be sent never fails the build.
- **The daily limit is 30 link saves per user** (spec L175, L262), enforced in `save_from_link` and nowhere else. The RPC takes `pg_advisory_xact_lock` on the user so that two saves at once can't both be the 30th, then counts that user's `link_saves` in the last 24 hours (a rolling window). Every link save counts: TikTok, YouTube, Instagram (even with nothing added) and plain links. Hand-written Recipes and Retries don't. Deleting a Draft doesn't give the save back. At the limit, the RPC returns `{ status: 'dailyLimitReached', limit: 30, retryAt }`, where `retryAt` is when the oldest save in the window turns 24 hours old. It creates no Recipe and builds nothing. The save screen then says "You've saved 30 links in the last 24 hours, the daily limit. You can save again at {time}." `link_saves` can't be written or deleted by users.
- **Tests and simulator**: the data-layer tests sign in a user, register a token, save 30 times (the 30th is `saved`) and check that the 31st is `dailyLimitReached`. With the recording `sendPush` fake, a finished Draft gives exactly one push to that user's tokens, and kicking it again adds none. On the simulator, tapping a notification is proved with `xcrun simctl push booted com.ant1007.recipeapp draft-ready.apns`, a fixture payload with the same `data`. If `getExpoPushTokenAsync` fails on the simulator, the app goes on without a token. Real delivery is checked by hand on TestFlight.

## User decisions for 03–07 (2026-10-26)

1. **Daily limit**: 30 saves in a rolling 24 hours; deleting a Draft doesn't give the save back.
2. **Build attempts**: 3 per Draft in total (the first plus two "Try again"); after that only "Fill in by hand".
3. **Search**: finds reviewed Recipes only, not unreviewed Drafts (default, not asked).
4. **Notification permission**: asked after the first saved link, not at first launch.
5. **Drafts**: a "Drafts (n)" row at the top of the Library, hidden when n is 0; no fifth tab.
6. **Suggested Tags**: shown already selected; the user removes the wrong ones (default, not asked).

## User decision: when a source can't be read (2026-10-27)

TikTok's oEmbed stopped returning `title`, `author_name` and `thumbnail_url` around 2026-10-19 (developer reports; no TikTok announcement); it now returns only the player iframe and `embed_product_id`. Big recipe sites (allrecipes, seriouseats) answer 402 to apps. The user chose to stay on official routes (ADR-0004), not to read TikTok's embed page:

- oEmbed stays the first try for TikTok (it may come back; the creator, thumbnail and caption are used whenever present).
- When the source gives no caption (TikTok's empty oEmbed) or refuses us (a recipe site's 4xx like 402/403), the Draft doesn't claim "recipe not in caption": it says the app couldn't read it, keeps the link (tapping it opens the video or page), and offers the ticket 05 paths: **paste the caption** or **add a screenshot**. Either builds the Draft through the same Draft builder, counted like a "Try again" (3 attempts in all).
- "Recipe not in caption" stays for a caption that was read and has no recipe.
- No scraping of TikTok's internal page data (`__FRONTITY_CONNECT_STATE__`, `__UNIVERSAL_DATA_FOR_REHYDRATION__`), and no browser User-Agent to get past a site's refusal.
- ADR-0004 gets a dated note recording this.
- (Ticket 05 review, 2026-10-27) "Paste caption" and "Add screenshot" are offered on any failed Draft and on a built one with no recipe found (an Instagram Reel saved with nothing), each counted toward the 3 builds.

Defaults chosen where the tickets leave things open. Override any by editing this file before the ticket starts. Implementers follow these; a reviewer treats a deviation as a finding. "Flag" bullets note where a ticket and the spec or the existing code disagree; the default given is what to build.

## 11 Usernames and Friends

- **Usernames** (spec L23, L25, L199): `profiles.username` stays nullable (null = not chosen yet) and gets `check (username ~ '^[a-z0-9_]{3,20}$' and username ~ '[a-z]')`: 3–20 characters, lowercase ASCII letters, digits and `_`, with at least one letter. The phone trims the input, drops one leading `@` and lowercases it before sending. Anything else is refused with "Use 3–20 letters, numbers or _". Because the stored value is always lowercase, the existing `unique` is case-insensitive in effect. Reserved names are refused like taken ones: `private.is_reserved_username(name)` holds a fixed list (admin, administrator, support, help, root, system, staff, team, official, moderator, mod, me, you, friend, friends, invite, api, www, app, settings, profile, account, login, signup, null, undefined) plus any name starting with `recipeapp`. `setUsername(name)` is the security-definer RPC `set_username`. It answers `{ status: 'set' | 'taken' | 'reserved' | 'invalid' }` and never raises on a clash. A username can be changed any number of times, and the old one is free at once. Friendships, requests and invite links refer to user ids, so nothing breaks. A user with no username (new, or anyone from before this ticket) sees a "Choose a username" screen after sign-in, before the tabs. Until they choose one, they can't be found and can't send requests.
- **Friendship** (spec L200): `friendships (requester_id, addressee_id, status friendship_status ('pending', 'accepted', 'declined'), created_at, responded_at)`, with one row per pair: a unique index on `(least(requester_id, addressee_id), greatest(…))` and `check (requester_id <> addressee_id)`. Accepted is mutual. **Users get no table grants on `friendships`.** Every read and write goes through security-definer RPCs: `send_friend_request(user_id)`, `respond_to_friend_request(requester_id, accept)`, `cancel_friend_request(user_id)`, `unfriend(user_id)`, `list_friends()` and `list_friend_requests()`. The table can't show the requester a `declined` status, so a decline is never revealed. Data-layer actions: `setUsername`, `searchUsers`, `sendFriendRequest`, `respondToFriendRequest`, `cancelFriendRequest`, `unfriend`, `listFriends`, `listFriendRequests` (incoming and outgoing).
- **The one rule for "is a Friend"** is `private.are_friends(a uuid, b uuid) returns boolean`: stable, security definer, `search_path = ''`, true only for an `accepted` row. `private.friend_ids(who uuid) returns setof uuid` wraps it for lists. Every later visibility rule calls one of these and nothing restates them, the same way decision 08 treats `private.ingredients_had`. The private schema isn't exposed through the Data API, so nobody can probe arbitrary pairs.
- **Request states**:
  - Sending to someone who already has a pending request to you accepts it. Both of you chose.
  - Sending while your own request is still pending or declined changes nothing and answers `requested`. You see it as "Requested" either way, so a decline is silent (spec L87).
  - Cancelling deletes your request, whether it's pending or was declined. You can then send a new one, but the push is limited (below).
  - Declining sets `declined`. The request leaves the addressee's list.
  - Accepting sets `accepted`.
  - Unfriending deletes the row, so neither side sees the other as a Friend (spec L89, L233). Either can send a new request later.
  - At most 50 outgoing pending requests per user (`{ status: 'tooMany' }`).
- **Profiles** become readable beyond your own: `private.can_see_profile(id)` is true for you, your Friends, both sides of a pending request, and co-members of any Cook Plan (14). Anyone else gets "not found", the same answer as an id that doesn't exist. A Profile shows only `id` and `username`.
- **Search** (spec L85, L193): `search_users(query)` is a security-definer RPC. It normalises the query like a username and returns nothing for under 3 characters. It returns up to 10 `{ id, username, relationship: 'none' | 'requestSent' | 'requestReceived' | 'friends' }` whose username starts with the query, exact match first, then alphabetical. It leaves out the caller and users with no username. A declined request still reads `requestSent`. It shows nothing but the username, there's no "list everyone", and the 3-character minimum and 10-result cap stop cheap enumeration. A per-user rate limit is a before-going-public item, not built now (see Questions 1).
- **Blocking**: no Block in v1. Moderation tools are out of scope (spec L284). Declining and unfriending are the tools, and the push limit below caps repeat requests (see Questions 3). Unfriending ends Shopping List sharing both ways (13) through a trigger on deleting a `friendships` row. Cook Plan memberships stay (spec L235).
- **Friend request push** (spec L88, L238) reuses the 07 sender:
  - `PushMessage.data` in `supabase/functions/_shared/push-sender.ts` widens to a union: `DraftReadyData | { kind: 'friendRequest'; fromUserId } | { kind: 'cookPlanInvite'; cookPlanId }` (14). It gets `friendRequestMessages(...)` beside `draftReadyMessages`.
  - A new thin Deno entry `supabase/functions/notify` (`POST {kind: 'friendRequest', toUserId}`) checks the caller's JWT. It then calls the service-role RPC `claim_friend_request_push(requester, addressee)`, which returns the requester's username and the addressee's tokens only if a pending request exists from the caller and no push went to that pair in the last 7 days. It records the push in `private.friend_request_pushes`. The entry sends through `expoPushSender` and forgets `DeviceNotRegistered` tokens with `forget_push_tokens`.
  - The data layer *kicks* it after `send_friend_request` answers `requested`, through a new `DataLayerOptions.sendNotification`, the way it kicks `build-draft`. Tests run it in-process with `recordingPushSender`. No pg_net trigger, for the reason in decision 03.
  - The push says title "Friend request", body "@{username} wants to be Friends". Tapping it opens Friends > Requests. A failed kick or send never fails the request: the in-app Requests list is the source of truth, with no retry. Accepting sends no push (spec L238).
- **Flag:** profiles are owner-read-only (`20261022235947_profiles.sql`) and `username` is nullable with a case-sensitive `unique`. This ticket adds the check and the wider read policy; it doesn't edit the old migration.

## 12 Invite links

- **Token**: `invite_links (token text primary key, inviter_id, created_at, expires_at, max_uses int default 20, uses int default 0, revoked_at)`. The server makes the token in `create_invite_link()` as 16 random bytes (`extensions.gen_random_bytes`), base64url, 22 characters. It lasts **7 days** and up to **20 redemptions**, one per redeemer, so it works in a group chat. Each user may have at most 5 live links and create at most 20 a day. `revoke_invite_link(token)` stops one. Users have no direct grants; only the inviter can list their own links, through the RPC.
- **URL**: a universal link `https://{INVITE_HOST}/i/{token}`. The app gets the Associated Domains entitlement `applinks:{INVITE_HOST}` (a new EAS build). The host serves an `apple-app-site-association` file that covers only `/i/*`, and a small static fallback page for people without the app. Both are plain files on a free static host. `recipeapp://invite/{token}` is accepted too, for Maestro and the fallback page's "Open in the app" button, but it's never what gets shared: WhatsApp and many chats don't make custom schemes tappable. Both routes open `src/app/invite/[token].tsx`. `INVITE_HOST` is an `EXPO_PUBLIC_*` value. **Blocked on a domain** (see Questions 2; the app name isn't decided, spec L296).
- **Sharing** uses React Native's `Share.share({ message: 'Add me on Recipe App: {url}' })`, with no new native module.
- **Redeeming** (spec L201): `redeemInvite(token)` calls `redeem_invite(token)`, which answers one of:
  - `requested`: a pending request from the redeemer to the inviter, plus the ticket 11 push to the inviter, body "@{username} opened your invite".
  - `accepted`: the inviter had already asked the redeemer, so they're now Friends.
  - `alreadyFriends`.
  - `own`: your own link does nothing.
  - `invalid`: unknown, expired, revoked and used up all give this one answer, so tokens can't be probed.

  It needs the redeemer to have a username. A user may redeem at most 20 invites a day; after that every answer is `invalid`. Redeeming the same link twice counts once.
- **Signed out, or no app**: with the app installed but signed out, the route keeps the token in AsyncStorage (`recipeapp.pendingInvite`, with its time). It's redeemed once after sign-in and the username step, then cleared, and the screen says "Friend request sent to @alex". A kept token over 7 days old is dropped. Only the latest is kept. Without the app, the fallback page links to TestFlight and says "Once it's installed, tap this link again". The Add Friend screen also has "Paste an invite link". We use no third-party deferred-deep-link SDK: they work by fingerprinting.
- **Flag:** ticket 12's "the friend request is created after first sign-in" can't happen with no action from the user. iOS passes no link through an App Store or TestFlight install. The default above (tap again, or paste) is the honest version.
- **Flag:** ticket 12 and spec L201 make the redeemer *request* the inviter, so the inviter still accepts. That's kept: links get forwarded, and spec L87 says only people I choose become Friends.

## 13 Share your Shopping List

- **Shares** (spec L215, L77–L81): `shopping_list_shares (list_id, friend_id, created_at)`, primary key `(list_id, friend_id)`. The owner shares with a Friend (`are_friends` checked in the RPC) and stops sharing. The Friend can leave (`leaveSharedShoppingList`). Actions: `shareShoppingList(friendId)` (spec L154), `stopSharingShoppingList(friendId)`, `listShoppingListShares()`, `listSharedShoppingLists()`. There's at most one list per owner (spec L215), so a Friend sees "Sam's list" beside their own in a switcher on the Shopping List tab.
- **Who may use a list** stays one rule. `private.can_use_shopping_list(list_id)` widens to: owner, **or** a share row for the caller **and** `private.are_friends(owner, caller)`. Unfriending therefore cuts access at once, even before the trigger from 11 deletes the share rows.
- **What a shared Friend can do**: read the list, add hand items, check off and uncheck any item, and remove hand-added items. Only the owner removes Ingredient lines or adds and removes Recipes: those come from the owner's Recipes and Pantry, and `add_recipe_to_shopping_list` and `remove_recipe_from_shopping_list` stay on `private.my_shopping_list()`. The item delete policy narrows to owner, or a Friend on a hand-added item. A Friend's check-off goes to the **owner's** Pantry (spec L79, L256). `check_off` already does this.
- **Recipe titles for Friends** (decision 09's "for ticket 13"): `shopping_list_amounts` gains `recipe_title text not null`, written when a Recipe is added. A trigger on `recipes` keeps it in step when `title` is updated. `toShoppingListItem` reads it in place of the `recipe:recipes(…)` join, which a Friend can't read (spec L190 keeps Recipes owner-only).
- **Offline** (spec L182, decision 10):
  - Every `ListChange` now names its list: `list: { kind: 'shoppingList'; id } | { kind: 'cookPlan'; id }` (15). Queued changes from before this ticket that don't name one are for the user's own list, read back first, as decision 10 handled older hand-adds.
  - There's still one queue per user (`recipeapp.listChanges.${me}`), across all their lists, in order. Each list gets its own cached copy (`recipeapp.shoppingList.${me}.${listId}`; the old key is read as the user's own list).
  - Decision 10's rule becomes "a queued change goes out only as the user who made it (`asSignedIn` unchanged), and only to a list the server says that user can use when it arrives". The rule isn't weakened, only widened from "their list" to "a list they can use".
  - `fetchShoppingList` reads by list id, not `.eq('owner_id', me)`.
  - A change to a list that's no longer shared with the user comes back `gone` and is dropped. When the next read finds the list gone, the phone says "Sam's list isn't shared with you any more. N changes weren't saved." and drops the cache.
- **Conflicts**: unchanged from decision 10. The later phone change wins by `phone_changed_at`, whichever phone made it, owner's or Friend's, with clock skew between phones accepted. Two people checking the same item: the first check keeps `checked_by` and is the only one that writes the Pantry.
- **Live** (spec L81, L238): Realtime Broadcast, not `postgres_changes`, because DELETE events can't be filtered and aren't checked by RLS. A statement trigger on `shopping_list_items`, `shopping_list_amounts` and `shopping_list_shares` calls `realtime.send('{}', 'changed', 'shopping_list:' || list_id, true)` (a private channel). A policy on `realtime.messages` lets a user receive a topic only when `private.can_use_shopping_list` passes for its id. The message carries no content. The phone re-reads the list (debounced 300 ms) while the list screen is open. There's no push for list changes (spec L282). If `realtime.send` is missing on the local stack, stop and ask.
- **When the friendship ends**: shares go both ways (spec L234). Items the Friend added stay, because the list is the owner's. `checked_by` stays, shown as "a former Friend" when their Profile can't be read.
- **Flag:** decision 09's note on the global `ingredients` table (any signed-in user can insert) is left as it is here, because sharing doesn't change who writes Ingredients. Moving those inserts into security-definer RPCs is a before-going-public item.

## 14 Start a Cook Plan

- **Model** (spec L216):
  - `cook_plans (id, creator_id, cook_on date null, status cook_plan_status ('active', 'cooked'), cooked_at, cooked_by, created_at)`. There's no title. A plan shows as its Recipe titles plus "with @sam, @jo · Sat 2 Nov".
  - `cook_on` is an optional calendar date with no time or zone (spec L100). Any member can set or clear it, and past dates are allowed. Nobody is notified.
  - `cook_plan_members (plan_id, user_id, invited_by, joined_at)`. `cook_plan_recipes (plan_id, recipe_id, added_by, added_at)`.
  - Caps: 8 members and 10 Recipes per plan.
  - The one membership rule is `private.is_cook_plan_member(plan_id, who)`, security definer.
- **Invites** (spec L94–L95, L111, L236): any member can invite **their own Friends** (`are_friends(inviter, invitee)` at invite time) to an active plan. Invitees don't have to be Friends with every other member. An invited Friend is a member at once and the plan appears for them (ticket 14). They can `leaveCookPlan`. When the last member leaves, the plan is deleted. Nobody removes anyone else in v1 (see Questions 4). Unfriended co-members both stay (spec L235). `are_friends` fails, so neither can invite the other into any plan: a new one, or one the other isn't in yet.
- **Invite push**: the same `notify` function as 11, `{ kind: 'cookPlanInvite', cookPlanId }`. The service-role `claim_cook_plan_invite_push(plan, invitee)` sends once per member per plan. Title "Cook Plan invite", body "@alex invited you to cook" plus the Recipe titles, if any. Tapping it opens the plan.
- **Recipes in a plan** (spec L96–L99, L192): a member adds one of their own **reviewed** Recipes. Any member removes any Recipe (spec L97). Members read every plan Recipe: one helper, `private.can_read_recipe(recipe_id)`, true for the owner or a member of any plan (active or cooked) the Recipe is in. It's used by the select policies on `recipes`, `recipe_lines` and `source_videos`. Ticket 19 extends the same helper. Writes stay owner-only. Tags, Want to Cook and Drafts never show. Another member's Instagram screenshot isn't readable (the owner-folder Storage policy, decision 05), so members see the plain Instagram card.
- **Your own copy** (spec L99, L204–L205, ADR-0002): `copyRecipe(recipeId)` calls the security-definer RPC `copy_recipe`, allowed when `private.can_read_recipe` passes. It makes a reviewed Recipe owned by the caller with the same title, steps and lines (the same Ingredient ids). Its Source Video row copies platform, URL, external id, creator, caption and thumbnail with the **original's `fetched_at`**, so decision 04's 30-day YouTube job still clears it on time. The screenshot isn't copied. Tags, Want to Cook, Cook Logs and Ranking aren't copied. New columns `copied_from_recipe_id` and `copied_from_user_id` (both `on delete set null`) are for display only: "Saved from @sam" while the Profile can still be read. Copying the same Recipe again makes another copy, but the screen offers "Open your copy" when one exists.
- **Deleting a Recipe that's in a plan** (spec L229–L232, L59): `deleteRecipe` stays as it is. A new `recipeCookPlans(recipeId)` lists the **active** plans it's in, so the screen can warn "It'll leave your Cook Plan with @sam" before deleting. Line handling is in 15.
- **Flag:** spec L231 says the Recipe leaves *every* Cook Plan, so it also disappears from cooked (archived) plans, and their history loses it. Built as written; the warning names only active plans.

## 15 The Cook Plan list

- **Items** (spec L216): `cook_plan_items (id, plan_id, ingredient_id, claimed_by, claimed_at, claim_changed_at, checked_at, checked_by, check_changed_at, created_at, updated_at)`, unique `(plan_id, ingredient_id)`. `cook_plan_amounts (item_id, recipe_id null, recipe_title, amount_texts, created_at)`, with `recipe_id` `on delete set null` and a title snapshot. There are **no hand-added items** on a Cook Plan list: spec L216 says an item is an Ingredient line.
- **Building it**: adding a Recipe runs the list engine's `toListLines([recipe])` with **no** `skip` (spec L178–L180). `add_recipe_to_cook_plan(plan, recipe, lines)` refuses Ingredients that aren't on the Recipe's lines (22023), as `add_recipe_to_shopping_list` does, and merges into existing lines. Amounts are never added together.
- **Who has it** (spec L102, decision 08): `cook_plan_who_has(plan_id)` is a security-definer wrapper that returns `(ingredient_id, user_id)` for every member, from `private.ingredients_had(member)`, **limited to the Ingredients on that plan's lines**. Only members may call it. It's computed on every read, never stored. No other part of anyone's Pantry is exposed. Unfriended co-members still see each other here (spec L235).
- **Claims** (spec L103–L104):
  - One claimer per item.
  - `claim` sets the caller as claimer, taking over a claim already there.
  - `unclaim` clears only the caller's own claim; anyone else's answers `gone`.
  - Claims show the claimer's username to every member.
- **Checking off** (spec L105, L181, L256): the checker is the buyer, and the Ingredient goes into **their** Pantry on the unchecked-to-checked change. Unchecking leaves the Pantry alone (decision 09). Checking off doesn't change the Claim.
- **Offline** (spec L106, L182): the same per-user queue as 13, with `{ kind: 'checkOff' | 'uncheck' | 'claim' | 'unclaim'; list: { kind: 'cookPlan', id }; itemId }`. The cache key is `recipeapp.cookPlanList.${me}.${planId}`. Each RPC takes `changed_at` and answers `applied | superseded | gone` as in decision 10, checking membership at send time. **Claims and checks keep separate phone timestamps** (`claim_changed_at`, `check_changed_at`), so one member's claim never beats another's later check-off. Last write wins within each. Adding or removing Recipes needs a connection.
- **Deleting or removing a Recipe** (spec L110, L229–L232, L259): a trigger on deleting a `cook_plan_recipes` row (from removing the Recipe, or the Recipe's deletion cascading) deletes that Recipe's amounts from items that are **unclaimed and unchecked**, and then deletes such items left with no amounts. On claimed or checked items the amount row stays, with `recipe_id` null and its title, shown as "{title} (removed)".
- **Live**: the Broadcast pattern from 13, topic `cook_plan:{id}`, on items, amounts, `cook_plan_recipes`, members and the plan row. The phone re-reads the plan.
- **After "We cooked it"** (18): Claim and unclaim answer `gone`. Check and uncheck still work, so a check made offline in the store still fills the buyer's Pantry.
- **Flag:** spec L182 lists "add" among queued Cook Plan changes, but the schema (spec L216) has no hand-added Cook Plan items. No add is built.
- **Flag:** editing a Recipe that's in a plan leaves its plan lines as they were, as ticket 21 found for Shopping Lists. Whatever 21 decides applies to both.

## 16 Cook Logs and the Saved/Cooked filter

- **Model** (spec L217, L115–L118):
  - `cook_logs (id, user_id, recipe_id, cooked_on date not null, notes text null check (length ≤ 2000), cook_plan_id null on delete set null, created_at, updated_at)`. The Recipe must be the logger's own and reviewed; `recipe_id` cascades on delete.
  - `cooked_on` defaults to the phone's local today and can't be later than tomorrow.
  - `cook_log_companions (cook_log_id, user_id)`: each must be a Friend of the logger, or a co-member of the log's Cook Plan when it came from one (18, spec L237). A companion stays on the log after an unfriend.
  - Actions: `addCookLog` (spec L157), `editCookLog`, `deleteCookLog`, `listCookLogs(recipeId)`.
  - A Recipe can have any number of Cook Logs (spec L117).
- **Photos** (spec L115): at most 4 per log, stored as the user's own images (ticket 16).
  - They live in a private bucket `cook-log-photos` at `{user_id}/{cook_log_id}/{photo_id}.jpg`, downscaled and saved as in decision 05 (1568 px, JPEG 0.8), and uploaded before the log is saved.
  - Storage select is allowed when the first path segment is the caller **or** `private.are_friends(segment, caller)`. Writes are owner-only.
  - Signed URLs last 1 hour.
  - Deleting a log removes its photos, best effort, as `removeScreenshot` does.
- **Who sees them** (spec L191, L258): the owner and their Friends, through `owner = caller or private.are_friends(owner, caller)` on `cook_logs`, `cook_log_companions` and the photos. Strangers and unfriended users see nothing. Friends see companions' usernames (spec L135) through a security-definer read. Companion usernames are already findable through search.
- **Saved/Cooked** (spec L55, L116): **Cooked** means a reviewed Recipe with at least one Cook Log. **Saved** means a reviewed Recipe with none, so deleting the last log makes it Saved again (ticket 16). Want to Cook stays its own list. `search_recipes` gains `cooked boolean default null` (null means all). The Library's `recipesFor` passes `cooked: filter === 'cooked'` for the two tiles, so the "Cooked" tile stops being visual-only (`src/app/(tabs)/index.tsx` line 105). Searching searches within the selected tile. `RecipeSummary` gains `cookCount` and `lastCookedOn`.
- **Flag:** the Library today shows *every* Recipe under Saved. Making Saved mean "not cooked yet" (ticket 16) hides cooked Recipes from the default tile (see Questions 6).

## 17 Ranking

- **What is ranked** (spec L218, L122–L130): the user's own Cooked Recipes (17's first criterion). There's one entry per Recipe: `ranking_entries (user_id, recipe_id unique, band ranking_band ('liked', 'fine', 'disliked'), position int, ranked_at)`, with positions 1…n contiguous in each band (1 = best) and a deferrable unique `(user_id, band, position)`. The Score is never stored.
- **Score** (spec L184, L187, L295) is one pure function, `scoreOf(band, position, bandSize)` in `src/data/ranking-engine.ts`, worked in integer tenths. Liked is 100 to 67, Fine 66 to 34, Didn't like 33 to 0: `round_half_up(hi10 − (hi10 − lo10) × i / (n + 1)) / 10`. So a lone Liked Recipe is 8.4, a lone Fine one 5.0 and a lone Didn't like one 1.7. The server returns band, position and band size; the engine makes every Score, mine and Friends' (19).
- **Comparisons** (spec L185, L79–L81): `startRanking(recipeId, band)` reads that band (best first, without this Recipe) and returns a `RankingSession`, which is pure state on the phone. The search is binary over the n+1 gaps: compare with the Recipe at `floor((lo + hi) / 2)`. "Better" moves up, "worse" moves down, and there is no "same", so there are no ties in order. That's at most `ceil(log2(n + 1))` comparisons, 7 for a band of 100 (17's criterion). `answerComparison(session, 'better' | 'worse')` returns the next session. `skipComparisons(session)` places the Recipe at gap `floor(n / 2)`, the middle (spec L186). The finished session calls `place_in_ranking(recipe_id, band, position, band_size_seen)`, which holds an advisory lock on the user. If the band's size changed meanwhile (another phone), it answers `bandChanged` and the phone restarts the comparisons. A session left half-way ranks nothing.
- **Ties in Score**: two neighbours in a big band can round to the same one-decimal Score. Order is still position. The badge shows the same number.
- **Re-ranking** (spec L188, L127): allowed any time from the Recipe screen, offered again after each new Cook Log. It removes the entry and inserts it again in one transaction, renumbering both bands.
- **Deleting** (spec L130, L188): deleting the Recipe cascades its entry, and a trigger renumbers that band. Deleting a Recipe's last Cook Log also removes its entry, after a warning, because only Cooked Recipes are ranked (see Questions 7).
- **Visibility** (spec L191): `owner = caller or private.are_friends(owner, caller)` on `ranking_entries`. Actions: `getRanking()` (spec L159) returns the three bands with Recipe title, thumbnail and Score.
- **Flag:** spec L80 says "about 3–5 comparisons with 100 cooked Recipes" and ticket 17 says "a band of 100 needs at most 7". They agree only if the 100 Recipes spread over three bands (about 33 per band means at most 6). Build to the binary-search bound.

## 18 "We cooked it"

- **Marking** (spec L107, L237): `markCookPlanCooked(planId)` (spec L156) lets any member set `status = 'cooked'`, `cooked_at` and `cooked_by`. Doing it twice is the same as once. There's no undo, so the screen confirms first. There's no push (spec L238).
- **Prompts** (spec L108): each member sees an in-app prompt card on the plan, and at the top of the Cook Plans tab, until they've logged every Recipe or tapped "Not now". The dismissal is `cook_plan_members.prompt_dismissed_at`. For each Recipe:
  - If the member owns it, they log it directly.
  - If not, they're offered "Save your copy first" (`copyRecipe`, or "Use your copy" when a copy with `copied_from_recipe_id` exists). The Cook Log and Ranking then attach to that copy (ticket 18).
  - The log form is pre-filled with `cooked_on` = the plan's `cook_on` if it's set and not in the future, else the local date of `cooked_at`; companions = every other member, including unfriended co-members (spec L237); and `cook_plan_id`.
  - After saving, "Rank it" opens 17's band picker, with Skip.
  - Every step can be dismissed (spec L108).
- **Archive** (spec L109): the Cook Plans tab has Active and Cooked sections, the Cooked ones newest first. Cooked plans are read-only except check and uncheck (15). Their Recipes stay readable to members through `private.can_read_recipe`.

## 19 Friend profiles

- **What it shows** (spec L134–L136): `getFriendProfile(userId)` (spec L159) returns:
  - username
  - "Friends since" (`responded_at`)
  - their Ranking by band with Scores, drawn in `friendAccent` (docs/design.md)
  - their Cook Logs newest first, 20 at a time: date, Recipe title, notes, photos, companions

  It never shows their Pantry, Staples, Shopping List, Want to Cook, Tags, Drafts, Recipes they haven't ranked or logged, or their Friends list.
- **Who can open it**: Friends only. A stranger, an unfriended user and an id that doesn't exist all get the same `not_found`, so a profile reveals nothing about who exists. A stranger can do no more than username search (spec L193).
- **Recipes on it** (spec L134, L136): `private.can_read_recipe` (14) widens to Recipes that have a Cook Log, or a Ranking entry, owned by a Friend of the caller. That covers title, lines, steps and Source Video link, but not the owner's screenshot. `copyRecipe` works on any of them (spec L136). Unfriending ends it at once (spec L234).
- **Flag:** spec L190 says Recipes are visible only to their owner (plus plan members, L192). Stories 87–89 need Friends to see and copy ranked and logged Recipes. The widening above is the default (see Questions 5).

## User decisions for 11–19 (2026-10-28)

1. **Username search:** matches the start of a username, from 3 characters, with at most 10 results. A rate limit comes before a public launch. (Default, not asked.)
2. **Invite links:** the user buys a neutral domain for universal links and the fallback page. `INVITE_HOST` is that domain, and ticket 12 waits until the user names it. There's no deferred-link SDK: after installing, people tap the link again or paste it.
3. **Block:** none in the TestFlight version. Declining stays silent, and a pair gets at most one request push every 7 days. Add Block before a public launch.
4. **Cook Plan invites:** invited Friends join at once and can always leave. (Default, not asked.)
5. **Recipe access:** Friends may read the full Recipe (lines, steps, video link) for anything in your Ranking or Cook Logs, and copy it. They never see Tags, Want to Cook, Drafts or Instagram screenshots. This widens spec L190, as §19 describes.
6. **Saved tile:** shows reviewed Recipes not cooked yet; Cooked shows those with at least one Cook Log.
7. **Last Cook Log:** deleting a Recipe's last Cook Log takes it out of your Ranking, after a warning. (Default, not asked.)
